1. Understanding CI/CD & Jenkins Core Concepts

Before diving into the codebase, it is essential to understand the foundational concepts of CI/CD and the terminology used within the Jenkins ecosystem.

What is CI/CD?

Continuous Integration (CI) is the practice of automating the integration of code changes from multiple contributors into a single software project. Continuous Deployment (CD) goes one step further by automatically deploying those integrated, tested changes to a production environment (such as our live web directory).

Jenkins Architecture & Terminology

To write and understand a Jenkins pipeline, you must be familiar with its building blocks:

  • Pipeline: A user-defined model of a CI/CD process. In our lab, this is written as code in a file named Jenkinsfile using Jenkins Declarative Pipeline syntax.
  • Node / Agent: A machine or container that connects to the Jenkins master to execute the pipeline tasks. Using agent any instructs Jenkins to allocate any available, capable node to run the build.
  • Stage: A logical block in the pipeline representing a major milestone (e.g., "Checkout", "Validate", "Deploy"). Stages allow us to visualize the pipeline's progress and isolate exactly where a failure occurs.
  • Step: A single, specific task executed within a stage. For example, running a Windows batch command (bat), printing text (echo), or pulling from a Git repository.
  • Workspace: A temporary, isolated directory on the agent node where Jenkins downloads the source code and executes the pipeline steps.

2. Architecture & Pipeline Logic

This project utilizes a fully automated CI/CD pipeline. Every time a collaborator pushes code to the central GitHub repository, Jenkins detects the change, validates the codebase in its workspace, and deploys the website to a local directory (C:\jenkins_site\).

Understanding our Jenkinsfile

The entire automation process is defined as code. Below is the exact Jenkinsfile driving our lab experiment. It operates in three distinct stages:

  • Stage 1 (Checkout): Instructs the agent to pull the latest source code from the main branch of the central GitHub repository into the workspace.
  • Stage 2 (Validate): Uses Windows Batch commands to ensure index.html and the students/ folder exist. If they are missing, it throws an exit code and halts the build to prevent a broken deployment.
  • Stage 3 (Deploy): Creates the target directory if it doesn't exist and uses xcopy to migrate the validated workspace to the production folder.
pipeline {
    agent any

    environment {
        DEPLOY_DIR = 'C:\\jenkins_site\\'
    }

    stages {
        stage('Checkout') {
            steps {
                echo '--- Stage 1: Checkout ---'
                git branch: 'main', url: 'https://github.com/yashkumbhoje/exp6-devops.git'
                echo 'Repository checked out successfully.'
            }
        }

        stage('Validate') {
            steps {
                echo '--- Stage 2: Validate ---'
                bat '''
                    IF NOT EXIST index.html (
                        echo ERROR: index.html not found!
                        exit /b 1
                    ) ELSE (
                        echo index.html found.
                    )

                    IF NOT EXIST students (
                        echo ERROR: students folder not found!
                        exit /b 1
                    ) ELSE (
                        echo students folder found.
                    )

                    echo Validation passed successfully.
                '''
            }
        }

        stage('Deploy') {
            steps {
                echo '--- Stage 3: Deploy ---'
                bat '''
                    IF NOT EXIST C:\\jenkins_site (
                        mkdir C:\\jenkins_site
                        echo Created deployment directory C:\\jenkins_site
                    )
                    xcopy /E /I /Y "%WORKSPACE%\\*" "C:\\jenkins_site\\"
                    echo Deployment to C:\\jenkins_site completed successfully.
                '''
            }
        }
    }

    post {
        success { echo 'Pipeline completed successfully! Site deployed to C:\\jenkins_site\\' }
        failure { echo 'Pipeline FAILED. Please check the logs above.' }
    }
}

3. Jenkins Platform Setup

Since each collaborator clones the repository to their own machine, you must configure your local Jenkins instance to listen to the central GitHub repository.

  1. Create the Pipeline Job

    Open Jenkins (http://localhost:8080). Click New Item, name it exp6-devops, select Pipeline, and click OK.

  2. Configure Automation Triggers

    Under Build Triggers, select Poll SCM and enter H/5 * * * * to check for GitHub updates every 5 minutes.

  3. Link the Repository

    Scroll down to the Pipeline section. Set Definition to Pipeline script from SCM. Set SCM to Git. Paste the Repository URL: https://github.com/yashkumbhoje/exp6-devops.git, and ensure the Branch Specifier is */main.

Note on Jenkins Triggers: Because we set the trigger to H/5 * * * *, Jenkins will automatically build within 5 minutes of any code being pushed. To bypass this wait time during our live lab, you can manually click Build Now on the left menu to force an instant deployment.

Step 3: Sync, Commit, and Push

⚠️ Merge Conflict Prevention (Important)

Because multiple classmates will be pushing code to the central repository at the exact same time during the lab, Git will block your push if someone else pushed a second before you. To fix this, you must run git pull origin main --rebase to merge their latest changes into your laptop before you push your own code.

Navigate back to the root folder, stage your file, sync with the server, and push to trigger Jenkins.
