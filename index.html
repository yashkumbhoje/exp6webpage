1. Understanding CI/CD & Jenkins Core Concepts

Before diving into the codebase, it is essential to understand the foundational concepts of CI/CD and the terminology used within the Jenkins ecosystem.

What is CI/CD?

Continuous Integration (CI) is the practice of automating the integration of code changes from multiple contributors into a single software project. Continuous Deployment (CD) goes one step further by automatically deploying those integrated, tested changes to a production environment (such as our live web directory).

Jenkins Architecture & Terminology

To write and understand a Jenkins pipeline, you must be familiar with its building blocks:

  • Pipeline: A user-defined model of a CI/CD process. In our lab, this is written as code in a file named Jenkinsfile using Jenkins Declarative Pipeline syntax.
  • Node / Agent: A machine or container that connects to the Jenkins controller to execute the pipeline tasks. Using agent any instructs Jenkins to allocate any available, capable node to run the build.
  • Stage: A logical block in the pipeline representing a major milestone (e.g., "Checkout", "Validate", "Deploy"). Stages allow us to visualize the pipeline's progress and isolate exactly where a failure occurs.
  • Step: A single, specific task executed within a stage. For example, running a Windows batch command (bat), printing text (echo), or pulling from a Git repository.
  • Workspace: A temporary, isolated directory on the agent node where Jenkins downloads the source code and executes the pipeline steps.

2. Architecture & Pipeline Logic

This project utilizes a fully automated CI/CD pipeline. Every time a collaborator pushes code to the central GitHub repository, Jenkins detects the change, validates the codebase in its workspace, and deploys the website to a local directory (C:\jenkins_site\).

Understanding our Jenkinsfile

The entire automation process is defined as code. Below is the exact Jenkinsfile driving our lab experiment. It operates in three distinct stages:

  • Stage 1 (Checkout): Instructs the agent to pull the latest source code from the main branch of the central GitHub repository into the workspace.
  • Stage 2 (Validate): Uses Windows Batch commands to ensure index.html and the students/ folder exist. If they are missing, it throws an exit code and halts the build to prevent a broken deployment.
  • Stage 3 (Deploy): Creates the target directory if it doesn't exist and uses xcopy to migrate the validated workspace to the production folder.
pipeline {
    agent any

    environment {
        DEPLOY_DIR = 'C:\\jenkins_site\\'
    }

    stages {

        stage('Checkout') {
            steps {
                echo '--- Stage 1: Checkout ---'
                git branch: 'main', url: 'https://github.com/yashkumbhoje/exp6-devops.git'
                echo 'Repository checked out successfully.'
            }
        }

        stage('Validate') {
            steps {
                echo '--- Stage 2: Validate ---'
                bat '''
                    IF NOT EXIST index.html (
                        echo ERROR: index.html not found!
                        exit /b 1
                    ) ELSE (
                        echo index.html found.
                    )

                    IF NOT EXIST students (
                        echo ERROR: students folder not found!
                        exit /b 1
                    ) ELSE (
                        echo students folder found.
                    )

                    echo Validation passed successfully.
                '''
            }
        }

        stage('Deploy') {
            steps {
                echo '--- Stage 3: Deploy ---'
                bat '''
                    IF NOT EXIST C:\\jenkins_site (
                        mkdir C:\\jenkins_site
                        echo Created deployment directory C:\\jenkins_site
                    )
                    xcopy /E /I /Y "%WORKSPACE%\\*" "C:\\jenkins_site\\"
                    echo Deployment to C:\\jenkins_site completed successfully.
                '''
            }
        }
    }

    post {
        success {
            echo 'Pipeline completed successfully! Site deployed to C:\\jenkins_site\\'
        }
        failure {
            echo 'Pipeline FAILED. Please check the logs above.'
        }
    }
}

3. Jenkins Platform Setup & Parameter Breakdown

To connect your local Jenkins instance to the central GitHub repository, you must create a Pipeline job and configure specific SCM parameters. Below is a detailed breakdown of each setting and why it is chosen.

Configuration Step-by-Step

  1. Create a New Pipeline Item

    Open Jenkins (http://localhost:8080). Click New Item, enter the item name as exp6-devops, select Pipeline as the project type, and click OK.

  2. Configure Build Triggers (Poll SCM)

    In the job configuration page, scroll down to Build Triggers and check Poll SCM. In the Schedule text area, enter H/5 * * * *.

  3. Link Pipeline Script from SCM

    Scroll down to the Pipeline section. Set Definition to Pipeline script from SCM, set SCM to Git, paste the Repository URL https://github.com/yashkumbhoje/exp6-devops.git, set Branch Specifier to */main, and verify Script Path is set to Jenkinsfile. Click Save.

Detailed Parameter Explanations

📌 Pipeline vs. Freestyle Project

Unlike legacy "Freestyle" projects where build steps are configured manually through the Jenkins GUI, a Pipeline project uses code (Jenkinsfile) to define all build stages. This provides repeatability, version control, and auditability for our automation workflow (Infrastructure as Code).

📌 Pipeline Script from SCM

This setting instructs Jenkins to fetch the build logic directly from the repository rather than hardcoding Groovy scripts in the Jenkins web console. This separates application logic from deployment execution and ensures any developer can update the pipeline by committing changes to Git.

📌 Poll SCM Syntax: H/5 * * * *

Poll SCM configures Jenkins to periodically inspect the remote Git repository for new commits without requiring external webhooks or tunnels (like Ngrok). The syntax follows Cron expression formatting:

  • H/5: Evaluates every 5 minutes. The H (Hash) symbol balances system load by distributing polling execution across different jobs.
  • * * * *: Represents (Hour, Day of Month, Month, Day of Week), ensuring the polling loop runs continuously 24/7.
📌 Branch Specifier: */main

Defines which target branch Jenkins monitors for incoming changes. Specifying */main ensures Jenkins ignores experimental development branches and triggers deployment pipelines strictly when commits land on the primary production branch.

📌 Script Path: Jenkinsfile

Specifies the relative file path within the root repository directory where the pipeline definition resides. Jenkins reads this exact file upon checking out the repository to execute the declared stages.

To demonstrate building an automated pipeline project from the ground up, we initialize a new repository named exp6-trial1, create the workspace structure, add baseline files, push to GitHub, and link it inside the Jenkins Dashboard UI.

Open your command line interface and run the following commands to provision the project workspace and subfolders:

:: 1. Navigate to Desktop and create project directory
C:\Users\kumbh\Desktop> cd C:\Users\kumbh\Desktop
C:\Users\kumbh\Desktop> mkdir exp6-trial1

:: 2. Create students subdirectory for team contributions

C:\Users\kumbh\Desktop\exp6-trial1> type nul > Jenkinsfile

Step 2: Initialize Git and Link to GitHub

Bind your local repository directory to the newly created remote repository on GitHub (`exp6-trial1`):

:: 1. Initialize local Git repository
C:\Users\kumbh\Desktop\exp6-trial1> git init

:: 2. Set primary branch name to main
C:\Users\kumbh\Desktop\exp6-trial1> git branch -M main

:: 3. Link remote GitHub repository
C:\Users\kumbh\Desktop\exp6-trial1> git remote add origin https://github.com/yashkumbhoje/exp6-trial1.git

:: 4. Stage all files
C:\Users\kumbh\Desktop\exp6-trial1> git add .

:: 5. Commit baseline files
C:\Users\kumbh\Desktop\exp6-trial1> git commit -m "Initial commit: exp6-trial1 pipeline setup"

:: 6. Push code to GitHub
C:\Users\kumbh\Desktop\exp6-trial1> git push -u origin main

Step 3: Create & Configure the Pipeline Job in Jenkins UI

Once the repository is pushed to GitHub, set up the corresponding automated job inside the local Jenkins Web Dashboard:

  1. Create the Job:

    Open http://localhost:8080 in your web browser. Click New Item on the left navigation panel. Enter the item name as exp6-trial1, select Pipeline, and click OK.

  2. Configure Automated Polling:

    Scroll down to the Build Triggers section, check the box for Poll SCM, and enter H/5 * * * * in the Schedule box.

  3. Connect SCM & Jenkinsfile:

    Scroll down to the Pipeline section and configure the following parameters:

    • Definition: Pipeline script from SCM
    • SCM: Git
    • Repository URL: https://github.com/yashkumbhoje/exp6-trial1.git
    • Branch Specifier: */main
    • Script Path: Jenkinsfile
  4. Save & Run Baseline Build:

    Click Save at the bottom. On the job dashboard, click Build Now to trigger your baseline build and verify deployment to C:\jenkins_site\.

5. Host Workflow (Project Initialization & Maintenance)

The host machine initializes the central repository structure and manages updates to templates and shared resources. Below are the core Git concepts and commands used to maintain remote state and handle concurrent updates.

Understanding Host Git Commands & Purpose

1. Repository Initialization & Remote Linking

Before files can be version-controlled, a local Git database must be initialized and linked to a central remote hosting platform (GitHub).

# Initialize local .git database
C:\Users\kumbh\Desktop\exp6-devops> git init

# Link local repo to central GitHub origin
C:\Users\kumbh\Desktop\exp6-devops> git remote add origin https://github.com/yashkumbhoje/exp6-devops.git
2. Staging Untracked Files, Deletions, and Updates

Executing git add . recursively inspects the current directory to stage modified files, newly created templates (untracked), and deleted files into the Git staging area before committing.

# Inspect working tree state
C:\Users\kumbh\Desktop\exp6-devops> git status

# Stage all additions, deletions, and updates
C:\Users\kumbh\Desktop\exp6-devops> git add .

# Create a local commit snapshot
C:\Users\kumbh\Desktop\exp6-devops> git commit -m "Chore: Add remaining student HTML templates"
3. Synchronizing Concurrent Changes via Rebase

When collaborators push code to GitHub concurrently, your local repository can fall behind remote state. GitHub rejects direct pushes with a ! [rejected] main -> main (fetch first) error to prevent overwriting existing commits.

Running git pull origin main --rebase fetches the latest remote changes and reapplies local commits on top of the remote history, maintaining a clean, linear commit log.

# Attempt push (rejected if remote contains newer commits)
C:\Users\kumbh\Desktop\exp6-devops> git push origin main
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/yashkumbhoje/exp6-devops.git'

# Fetch remote updates and reapply local commits on top
C:\Users\kumbh\Desktop\exp6-devops> git pull origin main --rebase
Successfully rebased and updated refs/heads/main.

# Push updated commits to remote repository
C:\Users\kumbh\Desktop\exp6-devops> git push origin main
To https://github.com/yashkumbhoje/exp6-devops.git
   6b9c971..ce8678f  main -> main

⚠️ Merge Conflict Prevention (Important)

Because multiple classmates will be pushing code to the central repository at the exact same time during the lab, Git will block your push if someone else pushed a second before you. To fix this, you must run git pull origin main --rebase to merge their latest changes into your laptop before you push your own code.
